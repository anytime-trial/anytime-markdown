# MCP ツールマニュアル（anytime 拡張が提供するサーバー）

MCP（Model Context Protocol）サーバーは、エージェントに「このワークスペース専用の道具」を渡す仕組みである。ファイルを端から読ませる代わりに、必要な答えだけを返す問い合わせ口を用意することで、コンテキストの浪費を防ぐ。

anytime 拡張は 4 系統のサーバーを提供する。

| サーバー | 担当 | ツール数 |
| --- | --- | --- |
| `mcp-markdown` | ドキュメントを探す・読む・書く・整える | 15 |
| `mcp-trail` | コード構造の探索、過去の経緯、レビュー・承認の記録 | 57 |
| `mcp-graph` | 図（`.graph`）と共起ネットワーク（`.cooc.json`）の作成と変換 | 15 |
| `mcp-cms` / `mcp-cms-remote` | S3 への文書・レポートの公開、Google ドキュメントの読み取り | 7 / 11 |

## 1. 前提条件

- Claude Code や Codex など、MCP に対応したエージェントを使っていること。
- ワークスペース直下に `.mcp.json` を置けること（サーバーの定義ファイル）。
- `mcp-trail` の解析実行系ツール（`analyze_*`）を使うなら、Trail 拡張のデータサーバーが起動していること。読み取り系と書き込み系はデータベースへ直接アクセスするため、サーバーが止まっていても動く。
- `mcp-markdown` の検索系ツールを使うなら、ドキュメント検索インデックスを一度構築してあること。
- `mcp-cms` を使うなら、S3 バケットと認証情報を環境変数に設定してあること。

## 2. サーバーを登録する

### 2.1. 拡張に登録させる

Markdown / Trail / Graph の 3 拡張は、**起動時に `.mcp.json` を見て、自分のエントリが無ければ追加する**。すでにエントリがあれば、内容が違っても上書きしない。利用者が独自にカスタムした定義を勝手に壊さないための挙動である。`.mcp.json` が壊れて解析できないときも書き換えない。

エントリを最新の内容へ更新したいときは、コマンドパレットから手動登録コマンドを実行する。

| 拡張 | コマンド |
| --- | --- |
| Anytime Markdown | `MCP サーバーを登録 (.mcp.json を書き出す)` |
| Anytime Trail | `MCP サーバーを登録 (.mcp.json を更新)` |
| Anytime Graph | `Anytime Graph: MCP サーバーを .mcp.json に登録` |

`mcp-cms` を登録する拡張は無い。§2.2 の方法で自分で書く。

### 2.2. `.mcp.json` を直接書く

```json
{
  "mcpServers": {
    "mcp-trail": {
      "command": "npx",
      "args": ["tsx", "packages/mcp-trail/src/stdio.ts"],
      "cwd": "/path/to/workspace",
      "env": { "TRAIL_WORKSPACE_PATH": "/path/to/workspace" }
    }
  }
}
```

**結果確認**: エージェントを再起動し、ツール一覧にサーバー名の付いたツールが並ぶこと。

### 2.3. サーバーのコードを変えたとき

MCP サーバーは標準入出力でつながる子プロセスとして動く。**VS Code を再読み込みしてもサーバーは入れ替わらない**。ツールの実装を変えたら、エージェント側で MCP を再接続する（Claude Code なら `/mcp reconnect`）。

この性質を知らないと、症状が「変更したはずのツールが古い挙動のまま」「追加したツールが一覧に出てこない」という形で現れ、実装側を疑って時間を溶かす。

## 3. mcp-markdown — ドキュメントを扱う

このプロジェクト群は「**知識の正本はベンダー中立な Markdown であり、データベースはそこから導出される検索インデックスにすぎない**」という原則を採る。`mcp-markdown` はその正本を探す側と書く側を担う。

| 目的 | ツール | 何をするか |
| --- | --- | --- |
| 探す | `search_docs` | 全文（FTS5）とメタデータ（種別・言語・カテゴリ）で文書を検索し、パス・タイトル・要約・抜粋を返す |
| 探す | `search_sections` | 見出しセクション単位で検索し、パス・見出し・階層・抜粋を返す |
| 探す | `grep_markdown` | 単一ファイル内をリテラル文字列で検索する（正規表現は使えない） |
| 構造を取る | `get_outline` | 見出し構造だけを平坦なリストで返す |
| 構造を取る | `get_frontmatter` | 本文を返さずフロントマターだけを返す |
| 部分を読む | `get_section` | 指定した見出しの本文だけを取り出す |
| 全文を読む | `read_markdown` | ファイル全文を返す |
| 部分を書く | `update_section` | 指定した見出しのセクションを置き換え、差分の要約だけを返す |
| 部分を書く | `update_frontmatter` | 本文に触れずフロントマターのキーを追加・削除する |
| 全文を書く | `write_markdown` | ファイルへ内容を書き込む |
| 整える | `format_markdown` | 見出し前後の空行・ブロック間隔・リストのインデント・末尾空白・テーブルのパイプを整える。冪等で、コードブロックとフロントマターには触れない |
| 整える | `sanitize_markdown` | Markdown を正規化・無害化する |
| 比べる | `compute_diff` | 2 つの Markdown（内容またはファイル）の差分を計算する |
| 辿る | `doc_backlinks` | 指定した文書へリンクしている文書を、関係の種別つきで返す |
| 辿る | `doc_neighbors` | 関係グラフを指定ホップ数だけ辿り、関連文書のパスを返す |

**大きな文書を丸ごと読ませない。** `search_docs` で当たりを付け、`get_outline` で構造を掴み、`get_section` で必要な節だけ取り出す。これが基本の順序である。

**書き込みにはパス範囲の制約がある。** 検索系はワークスペース外のドキュメントリポジトリまで届くが、読み書き・整形系はワークスペース配下しか触れない。検索で見つけたパスをそのまま編集ツールへ渡すと拒否されることがある。

## 4. mcp-trail — 構造と経緯を引き出す

`mcp-trail` は、コードの構造と、そこに至るまでの経緯を問い合わせるためのサーバーである。57 のツールを用途別に示す。

### 4.1. コード構造を探索する（読み取り）

変更に着手する前に、ここから入る。

| ツール | 何をするか |
| --- | --- |
| `get_important_files` | 重要度の高いファイルを順位つきで返す。`filter` で中心的・デッド・バレル・危険なファイルへ絞れる。**どこから読むかを決める起点** |
| `get_code_dependencies` | 指定ノードの依存元と依存先を返す。**変更前の影響範囲の確認**に使い、import の grep を畳む |
| `query_code_graph` | キーワードに一致するノードを重要度順に返す**検索専用**ツール。シンボルやファイルの所在当てに使う |
| `find_code_path` | 2 つのノード間の依存経路とホップ数を返す |
| `get_cochange_partners` | git 履歴で一緒に変更されるファイルを返す。import グラフが捉えない関連を補える |

**コードグラフ全体を読み込ませない。** 数十万トークン規模になり、コンテキストを使い切る。所在は `query_code_graph`、影響範囲は `get_code_dependencies` と、目的別に使い分ける。

### 4.2. 過去の経緯を引き出す

| ツール | 何をするか |
| --- | --- |
| `search_caravan_book` | 知識グラフを検索し、クエリに関連するエンティティ・関係・会話の記録を返す。**過去の決定や同種の不具合との接続を確認する入口** |
| `get_plan_context` | これから変更するファイルについて、未対処のレビュー指摘・再発バグ・決定・制約・共変更ファイルを、トークン量の上限つきで 1 回にまとめて返す。**着手前の文脈収集**に使う |
| `get_bug_causality` | バグ修正の因果カード（症状 → 根本原因 → 混入コミット → 前兆となったレビュー指摘 → 再発 → 関連する決定）を返す |
| `get_bug_history` | バグ修正の履歴を、影響ファイルと根本原因の参照つきで返す |
| `list_recurring_bugs` | 一定期間に繰り返し起きているバグのグループを返す |

### 4.3. レビューの記録を扱う

| ツール | 何をするか |
| --- | --- |
| `list_unaddressed_review_findings` | 未対処のレビュー指摘を、重大度・経過日数・対象ファイル・カテゴリで絞って一覧する |
| `get_review_history` | レビュー履歴を指摘つきで返す。指摘がバグへ発展した関係も含められる |
| `link_review_to_commit` | 指摘を特定のコミットで対処済みとして結びつける |
| `run_review_agent` | レビューの実行を登録し、実行 ID を即座に返す |
| `get_review_run_status` | 実行 ID からレビューの進行状況を取得する |
| `list_review_runs` | レビュー実行の履歴を絞り込んで一覧する |
| `list_review_target_hints` | ドリフト・バグ修正・未レビューのファイルから、優先してレビューすべき対象を提案する |

### 4.4. 承認と判断を記録する

要件書・設計書の承認（What 承認）をドクトリンへの先行承認に置き換える運用（`dev-operations` §0）で使う。

| ツール | 何をするか |
| --- | --- |
| `record_doctrine_judgment` | 人へ承認を求める**前に**、ドクトリンに接地した自分の判断を記録する。引用は実在の条項へ解決するか検査され、カバレッジゲートが代行の可否を判定する |
| `record_human_decision` | 人が実際に下した判断を記録し、AI の判断との一致を返す |
| `record_delegated_approval` | 代行（人に聞かずに進めたこと）を記録する。ゲートが代行可と判定し、自分の判断が承認で、人の判断がまだ無いときだけ受け付ける |
| `resolve_underspecified_points` | 「指示から一意に定まらない」と申告した論点に対する人の回答を記録する。回答が無い解消は受け付けない |
| `get_doctrine_agreement` | 一致率・エスカレーション率・引用の解決率・代行件数などを集計する |
| `get_acceptance_review` | セッションの受け入れ確認資料（代行した判断、引用した条項、成果物の差分、エスカレーションとその理由）を組み立てる |
| `evaluate_approval_policy` | ある操作が許可・確認・拒否のどれになるかを、運用設計領域の方針に照らして判定する。方針が宣言されていない操作は**許可にならず確認**に落ちる |
| `get_odd_policy` | 運用設計領域の方針がどこから来たか（設定ファイル / 既定 / 壊れている）を返す。**壊れた設定は既定で黙って置き換えない** |

**記録の無い代行はしない。** 記録に失敗したときは、人へ聞く側へ倒す。後から作れる代行記録は監査の役に立たないため、これらのツールは事後の書き込みを拒否する。

### 4.5. 指示の単位を宣言する

| ツール | 何をするか |
| --- | --- |
| `list_open_instructions` | まだ完了していない依頼を新しい順に返す。セッションの冒頭で、継続なのか新規なのかを判断するために引く |
| `record_instruction` | このセッションがどの依頼に属するかを宣言する。宣言しないと同じ作業が別々の行に分かれて記録される |

### 4.6. 設計と実装のずれを見る

| ツール | 何をするか |
| --- | --- |
| `check_alignment` | コードの変更に設計書が追随したかを判定する。`stale`（コードだけ変わった）/ `ok` / `undocumented`（宣言する設計書が無い）/ `unknown`（判定に要るコミットが未取り込み）を返す。**`unknown` を更新漏れと読まない** |
| `detect_drift` | 記録済みのドリフトを、未解決・重大度・種別などで絞って照会する |
| `explain_drift` | 個別のドリフトについて、会話・仕様・コード・バグ履歴・レビューの 5 方向から根拠を返す |
| `resolve_drift` | ドリフトを解決済みとしてメモつきで記録する |
| `list_boundary_drift` | 複数パッケージにまたがるコミュニティや、多数のコミュニティへ分裂したパッケージを警告として返す |

### 4.7. C4 モデルを参照・編集する

参照は `get_c4_model`（モデル全体）、`list_elements` / `list_relationships` / `list_groups`（ID 確認用の一覧）。

編集は `add_element` / `update_element` / `remove_element`（要素）、`add_relationship` / `remove_relationship`（関係）、`add_group` / `update_group` / `remove_group`（視覚的なグループ）。要素を消すと、それに紐づく関係も消える。グループを消しても所属要素は残る。

### 4.8. 解析を実行する

| ツール | 何をするか |
| --- | --- |
| `analyze_current_code` | C4 モデルとコードグラフの解析を起動する |
| `analyze_release_code` | リリース別の解析を行う。既存のリリース別グラフを**全削除してから**再生成する |
| `analyze_all` | セッションログを取り込み、コミット・リリース・カバレッジをデータベースへ書き込む |
| `get_analyze_status` | 進行中の解析の種別と開始時刻を返す |

これらは拡張のデータサーバーが起動していないと動かない。解析は対象規模によっては長時間かかる。

### 4.9. コミュニティに名前を付ける

`list_communities` / `list_community_nodes` で対象を把握し、`upsert_community_summaries`（名前と要約）と `upsert_community_mappings`（C4 要素との対応と役割）で書き戻す。知識グラフ側は `list_caravan_communities` と `upsert_caravan_community_summaries` を使う。

### 4.10. その他

| ツール | 何をするか |
| --- | --- |
| `get_verification_status` | 現在のコミットについて、どの検証（ユニット・ビルド・型・lint・E2E・手動）が成功済みかを台帳から返す。台帳は「何を実行したか」を答えるもので、「何を実行すべきか」は答えない |
| `get_threat_framework` | エージェントに対する脅威の枠組み（5 戦術・17 手法）を返す。データベースにも外部にもアクセスしない静的データ |
| `evaluate_reverse_spec` | 生成した設計書と基準の設計書を対にして、機械的なスコアと抜粋を返す。採点そのものは呼び出し側が行う |

## 5. mcp-graph — 図と共起ネットワークを扱う

図のドキュメント（`.graph`）と共起ネットワーク（`.cooc.json`）を作成・編集し、draw.io XML や SVG と相互に変換する。

| 目的 | ツール |
| --- | --- |
| 読み書き | `read_graph` / `write_graph` / `create_graph` |
| ノード操作 | `add_node`（グリッドに合わせて配置）/ `update_node` / `remove_node` / `list_nodes` |
| エッジ操作 | `add_edge` / `remove_edge`（ノードを消すと接続エッジも消える） |
| 一括生成 | `batch_import`（ノードとエッジの構造化データからまとめて生成） |
| 書き出し | `export_svg` / `export_drawio` |
| 取り込み | `import_drawio` |
| 共起ネットワーク | `write_cooccurrence` / `read_cooccurrence` |

**扱えるパスと拡張子が制限されている。** 書き込み先はワークスペース配下に限られ、範囲外は拒否される。図のツールは `.graph`、共起ネットワークのツールは `.cooc.json` しか受け付けない。

## 6. mcp-cms — 外部へ公開する

ローカルの Markdown や画像を S3 のバケットへ公開し、一覧・取得・削除する。**外部サービスへの送信を伴う**ため、公開してよい内容かを確認してから使う。

| ツール | 何をするか |
| --- | --- |
| `upload_report` / `list_reports` / `get_report` | レポートの投稿・一覧・本文取得 |
| `upload_doc` / `list_docs` / `delete_doc` | ドキュメント（Markdown・画像）の投稿・一覧・削除 |
| `read_google_doc` | サービスアカウント認証で Google ドキュメントをプレーンテキストとして読む |

必要な環境変数は、リージョン・バケット名・接頭辞・アクセスキーの 4 系統である。`read_google_doc` は**サービスアカウントの鍵ファイルのパスが設定されているときだけ登録される**。未設定でも他のツールには影響しない。使うには、対象の Google ドキュメントをサービスアカウントのメールアドレスへ共有しておく必要がある。

**鍵ファイルをリポジトリへコミットしない。**

リモート版（`mcp-cms-remote`）は同じ S3 機能を HTTP サーバーとして公開したもので、API キーによる認証が要る。加えて論文ランキングの収集（`get_unwritten_papers` / `mark_paper_written` / `list_paper_rankings`）とチケット起票（`create_ticket`）を持つが、いずれも対応する設定が揃っているときだけ登録される。

## 7. 使い分けの原則

1. **問い合わせで済むならファイルを読ませない。** ツールは必要な答えだけを返すが、ファイルを読ませると全文がコンテキストへ入る。
2. **構造の探索は目的別に。** 所在は `query_code_graph`、影響範囲は `get_code_dependencies`、読み始める場所は `get_important_files`。ひとつのツールで全部やろうとしない。
3. **着手前に経緯を引く。** `get_plan_context` か `search_caravan_book` で、対象ファイルの過去の決定・未対処の指摘・再発バグを確認してから変更に入る。
4. **文書は段階的に開く。** 検索 → 構造 → 節の順で必要な分だけ取り出す。
5. **書き込み系は範囲を確認してから。** `mcp-markdown` と `mcp-graph` はワークスペース配下しか触れない。`mcp-cms` は外部への公開である。

## 8. トラブルシューティング

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| ツールが一覧に出てこない | サーバーが登録されていない、または再接続していない | `.mcp.json` を確認し、エージェント側で MCP を再接続する |
| 実装を変えたのに古い挙動のまま | サーバーは子プロセスで、VS Code の再読み込みでは入れ替わらない | MCP を再接続する（§2.3） |
| 拡張の手動登録コマンドを実行しても定義が変わらない | 自動登録はエントリがあれば上書きしないが、手動コマンドは更新する。`.mcp.json` が壊れていると書き換えられない | JSON として妥当か確認する |
| 文書検索がエラーになる | 検索インデックスが未生成 | Markdown 拡張の索引再構築を実行する |
| 検索で見つけたファイルを編集できない | ワークスペース外は書き込み対象外 | 通常のファイル編集で扱う |
