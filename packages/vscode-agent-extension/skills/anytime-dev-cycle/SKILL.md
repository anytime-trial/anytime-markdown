# anytime-dev-cycle — 開発基本スキル

更新日: 2026-09-23

本体は入口判定・工程ルート・ゲートだけを持つ。提案、仕様、計画、実装、レビュー、回転、委譲の詳細手順は各スキルまたは `references/` へ委譲し、ここへ複製しない。

**高重大度の定義（本スキル共通・唯一の正本）**: 以下のいずれか 1 つでも該当すれば高重大度とする（OR 条件）。他ファイルで再定義せず本節を参照する。

- 永続データ（DB・ユーザー領域・保護領域）への書き込み・削除
- セキュリティ（認証・認可・シークレット・入力検証・サニタイズ）
- 公開経路（リモート push・本番リリース・Marketplace 公開・デプロイ・外部送信）
- 破壊的操作（`git reset --hard` / `clean -f` / `branch -D` / force push 等）

## 0. 入口 3 モード

| モード | 指示例 | 動き |
| --- | --- | --- |
| 開発サイクル（既定） | 「実装して」「直して」「一気通貫で」 | §1 で種別判定し、§2 の工程を必要分だけ順に実行 |
| 単発委譲 | 「Codex にやらせて」「ollama に投げて」 | サイクルを回さず `references/delegation.md` を読む |
| 単発回転 | 「サブエージェント回転で」「毎タスク compact」 | サイクルを回さず `references/agent-rotation.md` を読む |

モード判定が曖昧な場合だけ 1 回確認する。単発の「提案書を書いて」「技術記事を書いて」は `anytime-analysis` / `anytime-doc-authoring`、レビューだけは `pr-review-toolkit:code-reviewer` subagent / `anytime-cross-review`、リリースは `production-release` へ直行する。

### 0.5. プリフライト（事前チェック・初回必須）

ワークスペースルートで `node .claude/skills/anytime-dev-cycle/preflight.cjs` を実行し、環境前提と事前調査を検査する。

- **`--check` 指定時**: プリフライトのみ実行して結果を報告し、サイクル・単発モードは開始しない。
- **初回必須**: マーカー `<workspace>/.anytime/dev-cycle-preflight.json` が無い、または記録の `skillUpdated` が本ファイルの更新日と異なる場合、**どの入口モードでも本編開始前に必ず実行**する（結果はマーカーへ自動保存され、スキル更新まで再実行不要）。
- **必須 NG**（git/develop・docs リポ・スキル完全性 → exit 1）: サイクルを開始せず、観測事実を報告して中断する。
- **任意 NG**（codex CLI・ollama プロファイル・agent-core・並行セッション機構）: ルート宣言に縮退（当該実行手段を選ばない）を明記して続行する。
- **事前調査**（未完了プラン・git 概況）: §2.2 プラン三択と段0 の入力に使う。
- マーカーは環境チェック結果のキャッシュであり、承認状態・工程進捗は持たせない（ゲートは従来どおりその場の `ok`）。

## 1. ルート自動選択

### 1.1. 種別判定シグナル

| 種別 | 語彙 | 補助シグナル |
| --- | --- | --- |
| 新機能・振る舞い変更 | 追加、新機能、できるように、変更 | 外部から観測できる挙動が変わる |
| リファクタ・内部改善 | リファクタ、整理、分割、脱 any | 振る舞い不変が前提 |
| 不具合修正 | 直して、バグ、エラー、回帰、効かない | 再現手順・期待と実際の乖離がある |
| typo・deps・docs のみ | typo、バージョン上げ、ドキュメントだけ | コードの振る舞いに触れない |

競合・曖昧さがある場合のみ 1 回 AskUserQuestion で種別を確認する。セキュリティ修正は不具合修正ルートに含める。

### 1.2. 種別 × 工程

| 工程 | 新機能・振る舞い変更 | リファクタ・内部改善 | 不具合修正 | typo・deps・docs |
| --- | --- | --- | --- | --- |
| 段0 ブランチ確認 | ○ | ○ | ○ | ○ |
| 段1 提案書 | 明示指示時のみ | × | × | × |
| 段2 要件書・機能仕様書（What 承認） | ○ | ×（アーキテクチャ変更級のみ実施） | 設計書反映は振る舞い変化時のみ | × |
| 段3 実装計画（承認不要） | ○ | 3 ファイル以上なら○ | 3 ファイル以上なら○ | × |
| 段4 実装 | ○ | ○ | ○ | ○ |
| 段5 設計書更新・ドリフト検知 | ○ | 振る舞い不変なら不要 | 振る舞い変化時のみ | × |
| 段6 マージ前レビュー | ○ | ○ | ○ | docs・typo のみ省略可、deps は○ |
| 段7 develop ローカルマージ | ○ | ○ | ○ | ○ |

サイクル開始時に、判定種別・実施工程・省略工程と理由・**段4 の実行手段（`codex` / `main[EN]` / `subagent`）**を 1 ブロックで宣言する。ユーザーは上書きできる。黙って省略せず、省略可否を工程ごとに都度聞かない。

不具合修正では global `~/.claude/CLAUDE.md`「バグ修正時」へ委譲する。方針は提示せずベストプラクティス案で実装して採否理由を残し、fail するリグレッションテストを先行させる。本スキルで再定義しない。

## 2. 工程とゲート

| 段 | 内容 | 成果物 / 委譲先 | ゲート |
| --- | --- | --- | --- |
| 0 | ブランチ確認 | `git branch --show-current` + `.git/anytime/claims` | 永続ブランチ（master/main/develop）では作業せず、着手時に develop 由来の作業ブランチを作る。並行セッションが同一 worktree を保持していれば worktree で分離する |
| 1 | 提案書（明示指示時のみ） | `anytime-analysis` → `<docsRoot>/proposal/` | ファイル存在 + ユーザー `ok` |
| 2 | 要件書・機能仕様書の作成・改訂（AI） | `anytime-markdown-usage` + `anytime-markdown-output`（要件定義書・component spec・E2E シナリオ・試験設計書） | ファイル存在 + ユーザー承認（What の確定。実装前で唯一の内容承認） |
| 3 | 実装計画の作成（AI・承認不要） | プランファイルを `<docsRoot>/plan/` へ作成（構成は `anytime-doc-authoring` のプランファイル節） | ファイル存在のみ（承認ゲートなし。検証コマンドの実在確認は必須） |
| 4 | 実装 | §3 の手段選択 + `anytime-doc-authoring` §6（実装後テスト設計。旧 `anytime-impl-test-design`） | 出口から導出した検証が通過 |
| 5 | 設計書更新・ドリフト検知 | component spec / E2E シナリオ / 試験設計書 + mcp-trail 整合チェック | 振る舞い変更が正本へ反映済み + drift 検知 clean（未解消は是正 or 逸脱理由を記録） |
| 6 | マージ前レビュー | `pr-review-toolkit:code-reviewer` subagent / 高重大度（冒頭の定義）は `anytime-cross-review`（実装と別系統モデルで検証） | error/warn 解消、検証再確認 |
| 7 | マージ | develop へローカルマージ | push / リリースは別指示 |

### 2.1. ゲート判定

- ゲートは成果物ファイルの存在 + その場のユーザー承認（`ok` / `承認` / `進めて`）で判定する。
- 実装前にユーザー承認を取るのは段1（使用時）と段2（What の確定）のみ。段3 実装計画と実施内容にはユーザー承認ゲートを置かない（How は AI に委ね、結果の確認はリリース前の受け入れ試験＝人手のみ試験が担う）。
- **承認を求めるときは判断材料を添える**（承認の形骸化＝人が実質判断できないまま責任だけ負う状態を防ぐ）: 決定の根拠・却下した代替案とその理由・pre-mortem（想定される失敗シナリオ）を提示する。「承認してください」だけの要求をしない。
- 認知的摩擦は文脈依存で可変にする。低重大度・高可逆性の変更で承認を求めて摩擦の総量を増やさない。摩擦を上げるのは高重大度（§ 冒頭の定義）・不可逆な変更に限る。
- `APPROVED=true` のような状態フラグを発明しない。
- 承認は AskUserQuestion で取り、「修正する（前段へ戻る）」「中断する」を含める。

### 2.2. プラン三択と再開性

段3 の前に `<docsRoot>/plan/` から対象範囲が重なる未完了プランを探す。あれば新規作成より「継続・差分更新」を優先する。中断・セッション跨ぎ再開時は proposal / plan / component spec / review の存在を検査し、最初の未達ゲートから再開する。完了済み工程はやり直さない。

### 2.3. 各段の要点

- 段1: 明示指示時のみ。出力先は docs リポ `<docsRoot>/proposal/`。コード repo 内に置かない。
- 段2: 実装前に要件書・設計書を AI が作成・改訂し、ユーザー承認（What の確定）を得る。UI / 振る舞いを持つ機能は component spec だけでなく E2E シナリオ正本と試験設計書も author / 更新する。
- 段3: 3 ファイル以上の変更はプランファイルを作成する（再開性・plannedEdits 機械契約のため。承認は取らず作成後そのまま段4 へ）。検証コマンドは対象 `package.json` の scripts / devDependencies を事前確認する。
- 段3 の分解停止条件（contract-first）: 各タスクは**検証手段を先に決めてから**着手する。出力が主観的・観測不能で検証手段を書けないタスクは、実装に入らず分解し直すか、人手のみ試験（受け入れ試験）へ回すか、仕様の具体化（段2 へ戻る）を選ぶ。「実装してから検証を考える」順序を取らない。
- 段4: 実装後テストは出口から導出する。配線、mount、型、i18n、設定 schema、E2E、実機確認の必要性を `anytime-doc-authoring` §6（実装後テスト設計。旧 `anytime-impl-test-design`。手順詳細は同スキル references/impl-test-design.ja.md）で列挙する。実行手段は §3 の既定（Codex 委譲）と除外条件で決め、判定と見送りを記録する。
- 段5: 振る舞い・I/F・画面・データモデルが変わったら spec を更新する。enum / 設定値 / プリセット変更は兄弟値リテラルで横断 grep し、TS union、i18n、package schema、nls、設計書のミラーを同時更新する。docs リポ側の commit 規律は global / AGENTS.md に従う。
- 段5 ドリフト検知: 正本更新後に mcp-trail の `check_alignment` で「変更ファイル → C4 要素 → `c4Scope` を持つ設計書」の更新漏れ（設計書側の沈黙）を検査し、`detect_drift` で spec_vs_code の矛盾を確認する。検知した drift は是正（正本を更新）するか、意図的逸脱として理由を付けて `resolve_drift` で記録してから段6 へ進む。TrailDataServer 未起動で実行不能な場合は縮退（手動突合）をルート宣言に明記する。段5 自体を省略するルートでは検知も省略可。設計書ドリフトの週次デルタ監視は `anytime-dev-retro`（旧 anytime-dev-health）から本ゲートへ移管した（2026-07-14）。
- 段6: ユニット green だけを完了根拠にしない。型チェック、統合、実機、ビルドの必要分を再確認する。**実装と検証を同一モデルで完結させない**（同一基盤モデルは欠陥を共有し、AI レビュアー自身が騙され得る）。高重大度（冒頭の定義）の変更では `anytime-cross-review`（Claude × Codex の独立レビュー）を使い、それ以外は `pr-review-toolkit:code-reviewer` subagent でよい。レビュー指摘は鵜呑みにせず実測（再現・grep・テスト）で裏取りしてから採否を決める。
- 段7: ローカルマージのみ。push と本番リリースは明示指示時だけ。

## 3. 段4: 実行手段の選択

**先にループ形状を決める（プロンプトより前）**。手順が既知で終了条件が確定しているタスクに開放ループ（自律反復）を与えると堂々巡りになり、探索が要るタスクを固定手順に押し込むと途中で破綻する。着手前に 1 行で宣言する。宣言には形状・1 ターンの定義・終了条件に加えて**進捗指標**（何が減れば/増えれば前進か。例: 残り型エラー数・未通過テスト数・残タスク数・未対処指摘数）を含める。この指標が `stopping-rules-playbook.md` の無進捗観測「指標が 3 ターン以上変化していない」の判定対象になる — 未宣言のままでは無進捗検知が後手に回る（proposal `20260801-agentic-design-patterns-dev-cycle`）。

| ループ形状 | 選ぶ条件 | 1 ターンの定義 / 終了条件 |
| --- | --- | --- |
| 固定手順（workflow） | 手順が既知・分岐が少ない・結果が決定論的（リネーム・設定追加・定型移行） | 1 ターン = 手順 1 ステップ。全ステップ完了で終了。自律ループにしない |
| 反復ループ（generate → verify） | 実装＋検証を回す通常の実装（既定） | 1 ターン = 編集 + 検証 1 回。検証通過で終了。無進捗・失敗反復で中断（playbook） |
| 探索ループ（調査・デバッグ） | 原因・所在が未知で、収束するか事前に読めない | 1 ターン = 仮説 1 つの検証。仮説が尽きる / 予算超過 / 無進捗で中断し報告 |

探索ループで原因が確定したら、そのまま修正を続けず**反復ループへ切り替えて再宣言する**（バグ修正は「探索 → 反復」の 2 形状になるのが通常）。

**検証手段は生成の前に用意する**（verifier がループの荷重支持ステップ）。段3 が「検証手段を定義できるか」（計画時の分解可否）を見るのに対し、ここでは**着手直前にその手段が実際に使える状態か**を確認する（テスト・型チェック・ビルドが実在して実行できる、実機 / E2E の経路が通る）。定義はできたが実際には動かせないと判明したら、生成を始めずに段3 の分解停止条件へ戻る。

**段4 の実装タスクは Codex 委譲を既定とする。** メイン直執行を選べるのは下表の除外条件に該当する場合だけで、そのときはルート宣言へ除外 ID を明記する。「機械的か」「定型か」を主観で判定しない — どの実装タスクも「設計判断が絡む」と言えば除外できてしまうため、判定は客観入力を `delegation-triage.cjs` へ渡して機械的に決める。

```bash
node .claude/skills/anytime-dev-cycle/delegation-triage.cjs --paths packages/<pkg>/src/foo.ts \
  --files 3 --lines 120 --severity low --verify "npm test -w anytime-agent"   # → 実行手段: codex — 除外なし
```

| ID | 除外条件（該当時のみメイン直執行） | 判定入力 |
| --- | --- | --- |
| E1 | 高重大度（冒頭の定義。永続データ・セキュリティ・公開経路・破壊的操作） | `--severity high` |
| E2 | 変更 1 ファイル以下かつ 20 行未満（委譲契約を組む方が高くつく） | `--files` / `--lines` |
| E3 | 検証手段が実行不能（テスト・型・ビルドが実在しない） | `--verify` の実在検査 |
| E4 | 対話的な設計判断が実装と不可分（規範・設計の決定そのものが成果物） | `--interactive-design "<理由>"` |
| E5 | 委譲契約 6 点を組めない（対象パスが未確定） | `--paths` 未指定 |

サブエージェント回転は Codex 委譲の代替ではなく、多段・長い段階リストで**メイン文脈を守る運用機構**として併用する（`references/agent-rotation.md`。独立タスクは `always-fresh`、依存チェーンは `continue-while-cheap`）。ollama は実装・レビューの委譲先にしない（`references/delegation.md` §4.1）。

**fork と fresh の選び分け**: Agent ツールの `subagent_type: "fork"` は会話全体と prompt cache を継承し、**親モデルで動く**（`model` 指定は無視される）。fresh（fork 以外の型）は会話文脈を持たないが `model` を指定できる。global `CLAUDE.md` の委譲 3 条件のうち「独立した文脈で完結する」を満たさないタスクでも fork なら委譲できるが、親モデルで動くため §3.1 のモデル階層によるコスト低減は効かない。**コスト低減が目的なら fresh にモデルを明示し、会話文脈の再説明が委譲の価値を上回る場合だけ fork を使う**。なお CLAUDE.md と `~/.claude/rules/` は fresh でも継承される（2026-09-23 実測）。委任プロンプトへ書き写すのは、スキル本文と会話にしか無い前提（対象パス・直前の判断）だけでよい。

**判定は必ず記録する。** 委譲したタスクには `references/delegation.md` §2.2 の見積り・結果・実測行を、見送ったタスクには見送り行（`- 委譲見送り: [E2] <理由>`）をプランファイル（プランなしなら当日の作業記録）へ残す。記録の無い見送りは主観による除外と区別できず、委譲率を後から測れない。

プリフライトの `codex-cli` が NG の環境では既定を縮退し、ルート宣言に「codex 不在につきメイン直執行」と理由を書く（§0.5 の任意 NG 扱い）。

abstain 出口は `references/stopping-rules-playbook.md` 共通。abstained 返却は機械的に再委任せず、理由を評価して「前提修正後に再委任 / スキップ / ユーザーへエスカレーション」を明示選択する。モデル・effort 階層は §3.1 に従い、委譲時は `model` を明示する。

**委譲先の成果は委譲元が検証してから統合する（検証責任は転嫁できない）**。サブエージェント / Codex / ollama の「完了しました」は完了の根拠にならない。返り値を受けた側が実測（テスト実行・`git diff` 確認・対象ファイルの実在と内容確認）で裏取りし、乖離があれば統合せず差し戻す。委譲チェーンが多段でも、各段が直下の成果に責任を持つ（過去にサブエージェントの虚偽完了報告の実例あり）。

**実行中の適応トリガ**（検知したら継続せず停止・報告）の正本は `references/stopping-rules-playbook.md`。可逆な失敗は前提を直して再委任してよいが、不可逆・高重大度（冒頭の定義）の失敗は即時停止してユーザーへエスカレーションする（同 playbook「予算・不可逆性」）。

トークン効率の詳細は `references/agent-rotation.md` に委譲する。ここでは、独立・機械的タスクは small batch + fresh、継続が必要なチェーンだけ状態引き継ぎ、長時間ループでは main session 側の compact 前に制御状態を外部化する。

### 3.1. モデル・effort 階層

サブエージェント起動時は `model` パラメータを必ず明示する（省略すると親モデル＝メイン既定の高コストモデルを継承しコスト超過）。ユーザー指定があれば優先する。判断の順序は **(1) 作業を 4 軸で分類 → (2) 下表で初期割当（モデル × effort） → (3) 検証手段があれば低 effort で実行し失敗のみ昇格 → (4) 実測で較正**。effort が第一のレバーで、モデル変更は最後に置く（同一モデルで effort を下げる方が、モデルを一段下げるより品質を失いにくい。Anthropic 実測では上位モデルの `low` が下位モデルの `high` を上回る例が多く、比較は単価でなく完了タスク 1 件あたりコストで行う。根拠は `<docsRoot>/report/20260928-model-selection-method.ja.md`）。

**(1) 分類 4 軸**

| 軸 | 問い | 安いモデル・低 effort へ倒せる条件 |
| --- | --- | --- |
| 検証可能性 | テスト・型・ビルド・成果物実在で機械的に合否が出るか | 出る → 低 effort で実行し失敗のみ再実行できる |
| 失敗コスト | 誤りが不可逆か（永続データ・公開経路・破壊的操作） | 可逆 → 安い側。不可逆 → 上位モデル＋別系統レビュー |
| 文脈依存 | 会話の前提を再説明せずに完結するか | 完結 → fresh サブエージェントへ安いモデルを明示。要再説明 → fork（親モデル）か メイン |
| 探索の深さ | 手順既知（固定手順）か、原因未知（探索）か | 固定手順 → 安い側。探索・設計 → 上位モデル |

**(2) 初期割当（モデル × effort）**

| 作業 | 実行先 | effort | 根拠 |
| --- | --- | --- | --- |
| ファイル検索・Grep・ログ解析・整形確認 | **haiku**（`Explore` に `model: haiku`） | —（effort 非対応） | 出力が検証可能な大量処理 |
| 複数ファイル横断の読み取り調査 | **sonnet**（`Explore`） | `low` | 調査系の effort 曲線はほぼ平坦（`low` で 1〜3pt 減・コスト 1/3〜1/2） |
| 定型実装（対象・完了条件・検証が確定） | **Codex**（§3 の既定）/ sonnet | `medium` | 差し戻し率 5% 台で健全。Sonnet 5.5 は `medium` 起点 |
| バグ原因調査 | sonnet → 原因不明なら opus | `medium` → `high` | 探索ループ。再委任は一段昇格（下記） |
| コードレビュー | sonnet。高重大度は opus / Codex の別系統で二重化 | `medium` | 同一基盤モデルは欠陥を共有する |
| チャット・要約・分類・ドキュメント整形 | sonnet | `low` | 曲線平坦。`low` で思考を省く |
| 設計判断・アーキテクチャ・曖昧な要求 | メイン（委譲しない） | `medium` → `high` | 推論上限の作業。effort 1 段ごとに改善が続く |
| 長期自律実行（多段・自己検証つき） | **fable**（メインで実施。委譲先にしない） | `high` | fable の強みは旧世代が解けなかった領域。委譲先としてはメイン既定モデルに対する優位が無い |

**effort の指定経路**: メインは `/effort`。サブエージェントは `Agent` 呼び出しに effort 引数が無いため、`.claude/agents/<name>.md` の `effort:` frontmatter でのみ指定できる（定義の無い汎用型はセッションの effort を継承する。表の effort を効かせたい作業種別は定義ファイルを置く）。Codex は `codex exec -c model_reasoning_effort=<level>`（省略時は `~/.codex/config.toml` の値）。

**(3) 失敗のみ昇格**: 検証手段（テスト・型・ビルド）がある委譲は表の effort の 1 段下で実行し、失敗時のみ表の effort、次に一段上のモデルで再委任する（Anthropic 実測: `low` 全件 → 失敗のみ既定 effort で、合格率同等・コスト約半分）。検証手段が無い作業には適用しない（失敗を検出できないため表の effort から始める）。

**再委任時のモデル昇格**: 能力不足が疑われる差し戻し・abstain の再委任は、同条件・同モデルで繰り返さず（playbook「委譲先の異常」）、effort を 1 段上げる → haiku → sonnet →（opus / Codex / メイン自作）の順に 1 段ずつ昇格して行う。昇格しても失敗したらユーザーへエスカレーションする。昇格判断の材料は委譲結果行の `[model]` 記録（`references/delegation.md` §2.2）。逆に、初回選択を安易に安いモデルへ倒す免罪符にはしない（初回は上表の用途基準で選ぶ）。

**継続（`SendMessage`）はモデル指定を運べない**。ツールスキーマに `model` が無く、継続以降は親モデル（メイン既定＝高コスト側）で走る。安いモデルを明示したサブエージェントは継続せず fresh 回転で回す。回転ループは `shouldRotate` へ `delegatedModel` / `parentModel` を渡せば、系統が食い違う場合に閾値と無関係で回転を選ぶ（`references/agent-rotation.md`「コスト注意」）。

**(4) 較正**: 上表は初期値であり、`anytime-dev-retro` の `delegation.byModel`（採用率）と `activity_session_costs`（コスト）による 30 日窓の受動 Eval で改訂提案を受ける（`references/delegation.md` §2.3 と同じ経路）。Trail は effort を記録しないため、effort 列の効果は当面プランの委譲結果行に effort を併記して測る（例: `- 委譲結果: 雛形v2 [sonnet] 採用 — effort=low`。`[model]` 内に effort を入れると `grounding.cjs` の byModel キーが分裂する）。

### 3.2. 並行実行数

物理 96GB 環境では通常 4〜6 並列で問題ない。**事前の毎回確認は不要**で、OOM・swap・ビルド失敗を観測したときだけ `free -h` を確認し、available メモリで動的に絞る。

| 利用可能メモリ | 最大並行数 | ビルド/テストを含む場合 |
| --- | --- | --- |
| 30GB 以上（通常運用） | 6 | 4 |
| 15〜30GB | 4 | 2 |
| 6〜15GB | 2 | 1 |
| 6GB 未満 | 逐次実行 | 逐次実行 |

委任プロンプトの必須事項は global `~/.claude/CLAUDE.md`「サブエージェント」に従う。

## 4. ガードレール

- 永続ブランチ（master/main/develop）上で実装着手しない。着手時に作業ブランチを作る（コミット時点で気づいても、既に作業ツリーを他セッションと共有した後で worktree 分離の機会は失われている）。
- proposal / plan / review / spec は `<docsRoot>/` 配下へ出力し、コード repo 内へ置かない。
- ルート宣言なしに工程を黙って省略しない。
- 単発ドキュメント作成・レビュー・リリースを本スキルで乗っ取らない。
- 段2 の What 承認、段5 の正本更新、段6 レビューを軽く扱わない。docs・typo のみは段6省略可、deps は省略不可。
- 実装前の承認対象は要件書・設計書（What）のみ。プラン承認・実施内容承認のゲートを追加しない。
- 委譲先のエラーを silent に握りつぶさず、識別子付きで通知して中断 / 継続を確認する。
- 破壊的操作、push、リリース、force 系は明示指示時のみ。

## 5. アンチパターン

| 兆候 | 正す |
| --- | --- |
| develop に立ったまま着手した | 段0 は master/main だけでなく永続ブランチ全体が対象。作業ブランチを切るか worktree で分離してから着手する |
| ルート宣言なしに提案書やレビューを飛ばした | 種別・実施/省略工程・理由を宣言し、上書き可能にする |
| 新機能なのに段2（What 承認）を飛ばした | 段2 を実施し、要件書・設計書の承認を得てから実装する |
| 実装計画に承認を求めた・実施内容の承認を待った | 承認対象は What（段2）のみ。プランは AI 成果物として作成のみ、結果確認は受け入れ試験（リリース前の人手のみ試験）に委ねる |
| 不具合修正でテストなしに直した | global「バグ修正時」に戻り、failing regression test を先行し、方針は提示せずベストプラクティス案で実装 |
| 実装完了後に spec / E2E / 試験設計書が古い | 段5へ戻り、観測可能な変更を正本へ反映 |
| 段5 で正本を目視更新しただけで drift 検知を掛けなかった | `check_alignment` / `detect_drift` を実行し、未解消 drift の是正 or 逸脱理由の記録を済ませて段6 へ |
| 成果物を `/anytime-markdown/plan/` 等へ置いた | docs リポ `<docsRoot>/` へ作り直す |
| enum 追加を 1 ファイルだけで済ませた | 兄弟値リテラルで横断検索しミラーを更新 |
| 単発「提案書を書いて」を開発サイクルで処理した | `anytime-analysis` へ直行 |
| 委譲失敗を同じ条件で再委任した | `stopping-rules-playbook.md` に従い再委任 / スキップ / エスカレーションを選ぶ |
| 委譲先の「完了しました」を検証せず統合した | 委譲元が実測（テスト実行・`git diff`・対象ファイルの実在確認）で裏取りしてから統合する |
| エラーは出ないまま同じ場所を回り続けた | playbook「無進捗」の観測（同一ファイルの再読・編集の往復・変わらない検証結果）で中断し、方針を再評価する |
| ループ形状を決めずにプロンプトから書き始めた | §3 冒頭で形状（固定手順 / 反復 / 探索）と 1 ターン・終了条件を宣言してから着手する |
| 検証手段が無いまま実装量を増やした | 生成の前に検証手段（テスト・型・ビルド・実機）を確保する。用意できないなら段3 の分解停止条件へ戻る |
| 検証手段が決まらないタスクを実装から始めた | 段3 の分解停止条件に戻る。分解し直す / 受け入れ試験へ回す / 仕様を具体化する |
| 「承認してください」だけを提示した | 根拠・却下した代替案・pre-mortem を添える |
| マーカーが無い（初回）のにプリフライトを飛ばして本編に入った | §0.5。preflight.cjs を実行し、必須 NG なら中断・任意 NG は縮退を宣言 |
| 安いモデルを指定したサブエージェントを `SendMessage` で継続した | 継続は `model` を運べず親モデルで走る。fresh 回転に切り替えるか、親モデル課金でよいと明示的に判断する |
| 実装タスクを「設計判断が絡むから」でメイン直執行にした | §3 の除外条件 E1〜E5 に当たるか `delegation-triage.cjs` で判定し、当たらなければ Codex へ委譲する |
| 委譲を見送ったのに記録を残さなかった | 見送り行（`- 委譲見送り: [EN] <理由>`）をプラン / 作業記録へ残す。記録の無い見送りは主観の除外と区別できない |
