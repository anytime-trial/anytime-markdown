# ヒューリスティック評価チェックリスト（48 項目）

Phase 4（評価レポート）で使う項目レベルの評価観点。Nielsen の 10 原則を実務のチェック項目へ展開したもので、出典は `<docsRoot>/tech/UI_UXテスト観点リスト.md`（原典は note「実案件から学んだ、本当に役立つUIデザインの法則50」ほか）。

> 出典は「50 項目」と称するが、表の実数は **48 項目**である（原則別 9/4/4/4/4/4/4/9/3/3）。本書は実数に合わせる。

## 検出手段の分類

**この分類が本書の中核である。** 項目を並べただけのチェックリストは、外形観測で判定できない項目まで「未確認」として無言で落ちる。各項目がどこまで自動で判定できるかを先に決めておく。

| 区分 | 意味 | Phase 4 での扱い |
| --- | --- | --- |
| `auto` | `measure-ux.js` が判定する（実装済み） | 件数を実測し、根拠の種類は「規範照合」または「実測」 |
| `auto-todo` | 自動計測できるが未実装 | 現状は判定しない。**レポートに「未実装のため未判定」と書く** |
| `static` | 静的観測（スクリーンショット・DOM）で人が判定する | 判定は解釈を含むため、根拠の種類は「推定」 |
| `interactive` | クリック・入力・エラー誘発などの操作が要る | **現行 Phase 4 の範囲外**。レポートの「計測から除外した範囲」へ列挙する |
| `user-test` | 実ユーザーでしか判定できない | 未計測。必要な調査を書く |

内訳は `auto` 10 / `auto-todo` 6 / `static` 16 / `interactive` 21 / `user-test` 1（重複計上なし・合計 48。`auto` の 10 には部分判定 2 件を含む）。

**48 項目のうち 21 項目（44%）が操作を必要とし、静的な巡回だけでは判定できない。** 「チェックリストで評価した」と書くとき、この 44% が空欄であることを隠さない。

## Phase 4 での使い方

1. `auto` の 10 項目は `measure-ux.js` の出力から機械的に埋める。
2. `static` の 16 項目はスクリーンショットと DOM から人が判定し、**根拠の種類を「推定」**とする。
3. `auto-todo` の 6 項目は「自動計測できるが未実装のため未判定」と書く。**「問題なし」と書かない。**
4. `interactive` の 21 項目と `user-test` の 1 項目は、レポート §2 の「計測から除外した範囲」へ列挙する。
5. 検出した課題は `ux-report-template.md` の課題 ID（`UX-NN`）を振り、本書の項目 ID（`8-8` 等）を根拠として併記する。

## 評価手法の位置づけ

本スキルが行うのは**ヒューリスティック評価（エキスパートレビュー）**であり、開発早期に低コストで UI 欠陥を洗い出す手法である。次の限界が原理的に伴う。

| 手法 | 実施主体 | 本スキルとの関係 |
| --- | --- | --- |
| ヒューリスティック評価 | UI/UX 専門家 | **本スキルが行うもの。** 実際のユーザー挙動と乖離しうる |
| ユーザビリティテスト | 想定ユーザー | 行わない。SUS・タスク完了率・所要時間はここでしか得られない |
| 認知的ウォークスルー | 開発チーム・専門家 | 行わない。タスク単位の認知阻害要因は取れない |
| アイトラッキング | 想定ユーザー | 行わない |
| アンケート（SUS / NPS） | 一般ユーザー | 行わない |
| A/B テスト | 実運用トラフィック | 行わない |

ヒューリスティック評価の妥当性を上げるには本来 3〜5 名の独立した評価者が要る。**単一エージェントによる評価はこの条件を満たさない**ため、その旨をレポート §7 に書く。
